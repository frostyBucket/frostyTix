# frostyTix

I figured it's time to demonstrate some full stack skills on this account, so I went ahead and built a ticketing system! Read below if you're interested in my thought process throughout this project

The overall pipeline looks like this:

Electron - A pretty simple framework for developing desktop applications that can be used across multiple operating systems, and I knew I'd have an easy time getting the hang of it since I already had HTML and NodeJS in my toolbelt. My initial plan was to build this using the .NET framework, but it occurred to me that limiting part of your portfolio to Windows users isn't a very good idea (crazy revelation, I know). I made it a point to write out a basic draft before letting Claude do any work on it, since having it mimic the way I code made collaboration a lot more simple

Spring Web Services (on the backend) - Deciding between this and ExpressJS for the backend API was almost a challenge - Express would've taken slightly less time to set up, but Spring has a speed advantage, which I think is very important for a project that's meant to encourage collaboration within a team. The landing page uses simple HTTP since there's no need for a consistent connection there, and I built a web socket for the board page, as collaborative technology needs to be responsive.

PostgreSQL + OAuth (hosted via Google Cloud, for user data) - I went with OAuth for this project since it's a simple and efficient way to make sure that both A: Users have a secure way to log in, and B: Users FEEL secure letting the app know about their email. If I decided to add email alerts upon ticket assignment to a given user, the data's already there for me to implement a feature like that, which future-proofs the app for further development. The reason I went with PostgreSQL as opposed to the other available Google Cloud hosted database language (which I forgot the name of), is that I was already familiar with it. 

How I used Claude and why:
    I really only let Claude touch the frontend of this project, since I'm unwilling to pay for a subscription. So, while the overall architecture, the backend, and the way we implemented security were my doing, I can't take much credit for the code on the frontend. For most of the project, I'd make developments on the backend, create a zip file of the new stuff, and send it in with a detailed explanation of what each method or class was meant for. Then, Claude would send in an updated frontend in response that uses my new endpoints, and I'd test.
    We'd go back and forth like this for a while, and about halfway into the project (just before I'd started development on the websocket), I asked for genuine feedback about how I can personally progress as a developer. I would recommend anyone who consistently shows their own work to AI to try out this method, as I was given solid advice, and asking halfway into the project gave me the opportunity to implement what I was told for the remainder of the experience.
